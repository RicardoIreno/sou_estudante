# Diretrizes de Desenvolvimento

Regras gerais, válidas para todos os pacotes. Padrões específicos de cada pacote ficam nos documentos dedicados (ver *Padrões por pacote*).

## Princípio 0: simplicidade primeiro

- Comece pela solução mais simples que resolve o problema **atual**.
- Só crie abstração quando a dor já existir, não quando for imaginável. Regra dos dois usos: tolere duplicação até o segundo uso real; extraia a partir daí.
- Os princípios abaixo são meios, não metas. Se aplicar um deles aumenta a complexidade sem resolver um problema concreto, não aplique.
- Na dúvida, remova uma camada.

## Princípios

### 1. Núcleo funcional

- Prefira funções puras; isole efeitos colaterais nas bordas (I/O, rede, estado).
- Imutabilidade: não altere argumentos nem estado externo.
- Funções pequenas e com um único propósito. Extraia quando houver reuso ou quando o nome esclarecer a intenção; não fragmente em funções de uma linha sem ganho de clareza.

### 2. Qualidade e legibilidade

- Baixo acoplamento e alta coesão.
- Nomes autoexplicativos para variáveis, parâmetros e funções.
- Dependências explícitas por parâmetro; evite estado oculto de escopo externo.
- Use constantes nomeadas e tipadas para valores com significado de negócio ou usados em mais de um lugar. Não é necessário para literais óbvios usados uma única vez.

### 3. Modularização e divisão de arquivos

- Separe em arquivos quando um arquivo tratar mais de uma responsabilidade de domínio ou quando o tamanho prejudicar a leitura. Não crie um arquivo por função ou por parte por padrão.
- Nomeie o arquivo pela sua responsabilidade, no formato `<nome>.<papel>.ts` (ex.: `user.service.ts`, `date.utils.ts`). Convenções específicas de um pacote ficam no documento do pacote.
- Exporte apenas a API pública do módulo, reexportada pelo ponto de entrada (`index.ts`). Helpers internos não são exportados.

### 4. Desenvolvimento orientado a testes (TDD)

- Testes verificam comportamento por interfaces públicas, não detalhes de implementação.
- O código pode mudar por completo; os testes não.
- Um bom teste lê como uma especificação: "usuário consegue finalizar a compra com carrinho válido" diz qual capacidade existe e sobrevive a refatorações.
- Teste o conjunto pela API pública, não cada peça interna separadamente.
- Diretrizes de testes: [tdd-specs/tests.md](tdd-specs/tests.md)
- Diretrizes de mocks: [tdd-specs/mocking.md](tdd-specs/mocking.md)

## Ciclo Red → Green → Refactor → Commit

1. **Red:** escreva um teste que falha e crie apenas o mínimo necessário para ele compilar. A estrutura do código emerge dos testes, não é planejada antes.
2. **Green:** escreva o código mais simples que faz o teste passar.
3. **Refactor:** com os testes verdes, melhore o teste e o código.
4. **Commit:** uma mensagem de uma linha, com os testes passando.

Etapas adicionais específicas de um tipo de pacote (ex.: stories em componentes visuais) ficam no documento do pacote.

### Confirmação com o usuário

Confirme ao final de cada ciclo completo e **antes de decisões estruturais** (nova abstração, novo padrão, nova dependência). Não é necessário confirmar a cada passo.
