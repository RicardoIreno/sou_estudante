# Operação

Como o projeto é publicado e operado. Este documento descreve o que existe hoje;
lacunas conhecidas estão em [Limitações](#limitações-conhecidas).

> Escopo atual: só a seção de **deploy**. Setup local, variáveis de ambiente e
> diferenças entre dev e produção ainda serão acrescentados (ver
> [analise-sonnet.md](analise-sonnet.md), seção 8).

## Deploy

O deploy é feito do GitHub Actions para uma VM de produção, via **SSH + rsync**.
O workflow roda em um runner hospedado pelo GitHub (`ubuntu-latest`) e publica o
código na VM usando um script remoto (`scripts/deploy.sh`).

### Gatilho

O workflow [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) roda em:

- `push` na branch `main`;
- execução manual (`workflow_dispatch`).

Execuções de deploy não se sobrepõem (`concurrency: deploy-vm`, sem cancelar a
que está em andamento). O deploy usa o environment `production` do GitHub
(repositório → Settings → Environments), onde ficam os secrets abaixo.

### Etapas

1. **`lint`** e **`test`** (workflows reutilizáveis `lint.yml` e `test.yml`). O
   deploy só começa se os dois passarem:
   - formatação: Biome (front) e `gofmt` (API);
   - API: `go mod tidy -diff`, `go vet`, `go test`;
   - front: `tsc --noEmit`, `vitest run`, `next build`.
2. **`deploy`**, em runner `ubuntu-latest`, com limite de 30 min. Executa, nesta
   ordem:
   1. **checkout** do repositório (no runner);
   2. **configura o SSH**: escreve a chave privada, o `known_hosts` e um host
      alias `deploy` em `~/.ssh/config`. Falha se faltar algum dos secrets
      `SSH_HOST`, `SSH_USER`, `DEPLOY_PATH`, `SSH_PRIVATE_KEY` ou `SSH_KNOWN_HOSTS`;
   3. **`rsync`** do código para `DEPLOY_PATH` na VM. O `--delete` remove arquivos
      que saíram do repositório, mas `.env`, `data/`, `.git/`, `.github/`,
      `node_modules/`, `.next/`, `coverage/` e `packages/api/tmp/` são
      preservados no servidor (ver [Pré-requisitos no servidor](#pré-requisitos-no-servidor));
   4. **`ssh deploy "cd DEPLOY_PATH && IMAGE_TAG=${GITHUB_SHA} bash scripts/deploy.sh"`**,
      que roda na VM (ver [scripts/deploy.sh](#scriptsdeploysh));
   5. **remove a chave privada** do runner (`if: always()`).

### `scripts/deploy.sh`

Roda **no servidor**, dentro de `DEPLOY_PATH`. Pode ser executado à mão
(`IMAGE_TAG=<sha> scripts/deploy.sh`) para repetir uma publicação. Etapas:

1. falha se `.env` não existir, **ou** se `ELASTIC_PASSWORD` e
   `ELASTICSEARCH_APIKEY` estiverem vazias;
2. detecta o comando de compose disponível (ver [Pré-requisitos no servidor](#pré-requisitos-no-servidor));
3. `build --pull` (com `IMAGE_TAG=${GITHUB_SHA}`, versiona as imagens pelo commit);
4. `up -d --remove-orphans`;
5. remove imagens órfãs (`image prune -f`);
6. verifica a saúde (ver [Verificação pós-deploy](#verificação-pós-deploy));
7. mostra o `ps` dos containers.

Variáveis opcionais: `IMAGE_TAG` (padrão `latest`), `COMPOSE_FILE` (padrão
`docker-compose.prod.yml`).

### Secrets necessários

No environment `production` do GitHub:

| Secret | Uso |
| --- | --- |
| `SSH_HOST` | endereço da VM de produção |
| `SSH_USER` | usuário SSH usado para conectar |
| `SSH_PORT` | porta SSH (padrão `22`) |
| `DEPLOY_PATH` | pasta onde o código é sincronizado na VM |
| `SSH_PRIVATE_KEY` | chave privada usada para autenticar |
| `SSH_KNOWN_HOSTS` | conteúdo do `known_hosts` (pin do host) |

### Pré-requisitos no servidor

- Acesso SSH para o usuário configurado (`SSH_USER`), com permissão de escrita em
  `DEPLOY_PATH`. O `rsync` cria a pasta se não existir.
- Arquivo `.env` em `DEPLOY_PATH`, **criado à mão** (o deploy não o gera; o
  `rsync` preserva o existente). Parta de `.env.example`. As API keys
  (`ELASTICSEARCH_APIKEY`, `ELASTICSEARCH_BULK_APIKEY`) são geradas pelo `setup.sh`.
  `ELASTIC_PASSWORD` e `ELASTICSEARCH_APIKEY` são obrigatórias e validadas pelo
  `deploy.sh`.
- Algum comando de compose disponível; o script tenta, nesta ordem:
  `podman compose`, `podman-compose`, `docker compose`, `docker-compose`.
- Arquivos de dados em `./data` (ver abaixo), se for rodar o seed.

> O servidor **não precisa** de `git` nem do repositório clonado: o `rsync` envia
> o código direto do runner e exclui `.git/` da sincronização.

### Imagens

O `docker-compose.prod.yml` nomeia as imagens `sou_estudante/{api,front,seed}:${IMAGE_TAG:-latest}`.
O workflow define `IMAGE_TAG=${GITHUB_SHA}`, então cada publicação gera imagens
marcadas pelo SHA do commit (sem sobrescrever `latest`). A tag `latest` só é usada
em deploys manuais fora do workflow.

### Seed (ingestão de dados)

**O deploy não roda o seed.** Os índices do Elasticsearch persistem no volume
`elsou-data`. Para carregar ou recarregar dados, com os JSON em `./data`
(`dados_curso_completo.json` e `dados_ies.json`), no servidor:

```bash
podman compose -f docker-compose.prod.yml --env-file .env --profile bulk run --rm --no-deps se_bulk
```

O seed só reingere um índice que não existe ou está vazio. Ver os riscos de
ingestão parcial em [analise-sonnet.md](analise-sonnet.md), seção 9.

### Verificação pós-deploy

- O `deploy.sh` verifica, nesta ordem, por até ~60 s cada (30 tentativas, 2 s):
  - Elasticsearch (`http://localhost:9200/`): aceita HTTP 200 ou 401 (o `401` já
    indica que está no ar, pois a autenticação está habilitada);
  - API (`http://localhost:8080/healthz`): liveness, não consulta o Elasticsearch;
  - front (`http://localhost:3000/`).
- A API e o Elasticsearch publicam suas portas em `127.0.0.1` na produção, portanto
  as checagens são feitas dentro do servidor (o front publica `3000` em todas as
  interfaces).

### Rollback

**Não há rollback automatizado.** Como cada publicação reconstrói as imagens a
partir do código sincronizado, voltar a uma versão anterior é feito pelo Git:

1. Reverter o commit problemático na `main` (`git revert <sha>`) e fazer push. O
   workflow publica a versão revertida. Este é o caminho recomendado: mantém o
   histórico e passa pelo CI.
2. Em emergência, na VM: sincronizar a versão anterior em `DEPLOY_PATH` (por
   exemplo, reexecutando o `rsync` a partir do `sha` bom) e repetir
   `IMAGE_TAG=<sha> bash scripts/deploy.sh`. O próximo push na `main` volta a
   sobrescrever esse estado.

Os dados do Elasticsearch não são revertidos por nenhum dos dois caminhos.

## Limitações conhecidas

- Sem staging; o deploy vai direto para a `main`/produção.
- `.env` de produção fora do controle de versão (só `ELASTIC_PASSWORD` e
  `ELASTICSEARCH_APIKEY` são validadas; as demais não).
- Sem rollback automatizado (a versionagem por `IMAGE_TAG` facilita, mas o
  rollback continua sendo via Git).
- Sem health check semântico (o `/healthz` é só liveness; não valida a
  comunicação da API com o Elasticsearch).
- O seed é manual.
