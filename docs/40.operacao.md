# Operação

Como o projeto é publicado e operado. Este documento descreve o que existe hoje;
lacunas conhecidas estão em [Limitações](#limitações-conhecidas).

> Escopo atual: só a seção de **deploy**. Setup local, variáveis de ambiente e
> diferenças entre dev e produção ainda serão acrescentados (ver
> [analise-sonnet.md](analise-sonnet.md), seção 8).

## Deploy

### Gatilho

O workflow [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) roda em:

- `push` na branch `main`;
- execução manual (`workflow_dispatch`).

Execuções de deploy não se sobrepõem (`concurrency: deploy-vm`, sem cancelar a
que está em andamento).

### Etapas

1. **`lint`** e **`test`** (workflows reutilizáveis `lint.yml` e `test.yml`). O
   deploy só começa se os dois passarem:
   - formatação: Biome (front) e `gofmt` (API);
   - API: `go mod tidy -diff`, `go vet`, `go test`;
   - front: `tsc --noEmit`, `vitest run`, `next build`.
2. **`deploy`**, em um runner `self-hosted` (a VM de produção), com limite de 30 min.
   Executa, nesta ordem:
   1. `cd /var/www/sou_estudante`;
   2. `git fetch` + `git reset --hard origin/main` (alterações locais no
      servidor são descartadas);
   3. falha se `.env` não existir nessa pasta;
   4. `podman compose -f docker-compose.prod.yml --env-file .env build --pull`;
   5. `podman compose ... up -d --remove-orphans`;
   6. `podman image prune -f`;
   7. testa `http://localhost:3000/` por até ~60 s (30 tentativas, 2 s);
   8. mostra `podman compose ... ps`.

### Pré-requisitos no servidor

- Repositório clonado em `/var/www/sou_estudante` (caminho fixo no workflow).
- Arquivo `.env` na raiz do clone, **criado à mão** (o deploy não o gera). Parta de
  `.env.example`. As API keys (`ELASTICSEARCH_APIKEY`, `ELASTICSEARCH_BULK_APIKEY`)
  são geradas pelo `setup.sh`.
- `podman` e `podman compose` disponíveis para o usuário do runner.
- Arquivos de dados em `./data` (ver abaixo), se for rodar o seed.

### Imagens

O `docker-compose.prod.yml` nomeia as imagens `sou_estudante/{api,front,seed}:${IMAGE_TAG:-latest}`.
O workflow não define `IMAGE_TAG`, então toda publicação sobrescreve a tag `latest`.

### Seed (ingestão de dados)

**O deploy não roda o seed.** Os índices do Elasticsearch persistem no volume
`elsou-data`. Para carregar ou recarregar dados, com os JSON em `./data`
(`dados_curso_completo.json` e `dados_ies.json`), no servidor:

```bash
podman compose -f docker-compose.prod.yml --env-file .env --profile bulk run --rm --no-deps se_bulk
```

O seed só reingere um índice que não existe ou está vazio. Ver os riscos de
ingestão parcial em [analise-sonnet.md](analise-sonnet.md), seção 9.

### Verificação pós-deploy

- O workflow só confirma que o front responde na porta 3000. Não verifica a API
  nem o Elasticsearch.
- A API expõe `GET /healthz` (apenas liveness, não consulta o Elasticsearch). Na
  produção a API publica a porta em `127.0.0.1`, portanto a checagem é feita
  dentro do servidor.

### Rollback

**Não há rollback automatizado.** Como o deploy sempre faz `reset --hard origin/main`
e reconstrói as imagens, voltar a uma versão anterior é feito pelo Git:

1. Reverter o commit problemático na `main` (`git revert <sha>`) e fazer push. O
   workflow publica a versão revertida. Este é o caminho recomendado: mantém o
   histórico e passa pelo CI.
2. Em emergência, no servidor: `git reset --hard <sha-bom>` em
   `/var/www/sou_estudante` e repetir `build` e `up -d` do passo 2. O próximo push
   na `main` volta a sobrescrever esse estado.

Os dados do Elasticsearch não são revertidos por nenhum dos dois caminhos.

## Limitações conhecidas

- Caminho do servidor fixo no workflow; sem staging.
- `.env` de produção fora do controle de versão e sem validação de variáveis.
- Sem versionamento de imagens (`latest` sempre) e sem rollback automatizado.
- Sem verificação de saúde da API e do Elasticsearch no deploy.
- O seed é manual.
