# Diretrizes de Composição de Componentes

*Guia de padrões para componentes React: começar simples, complicar só com motivo.*

## 1. Princípio central

**O padrão mais simples que resolve o problema de hoje é o correto.** Compound Component, Agnóstico + Wrappers, Context e generics são ferramentas para problemas específicos, não o ponto de partida. Cada camada de abstração tem custo: mais arquivos, mais indireção, mais coisas para um novo desenvolvedor entender antes de mexer em qualquer coisa.

Regras de bolso:

- Comece com um componente e props simples.
- Só introduza um padrão quando a dor dele já existir, não quando for imaginável.
- Se você precisa explicar a estrutura por mais de um minuto para alguém do time, provavelmente ela está complexa demais.
- Duplicar um pouco de código é melhor do que criar a abstração errada.

## 2. Como escolher: árvore de decisão

Responda na ordem e **pare na primeira resposta "sim"**.

1. **Um componente com props resolve?** (poucas props, sem partes opcionais ou reordenáveis) → **Props simples.** Fim.
2. **O consumidor só precisa trocar variante, tema ou tom?** → **Props simples** (`variant`, `tone`). Se for propagar para filhos profundos, use **Scoped-Variable** (seção 5).
3. **O consumidor precisa reordenar, omitir ou intercalar partes da estrutura?** → **Compound Component** (seção 4).
4. **O mesmo componente será usado por 2 ou mais domínios com dados/textos diferentes?** → **Agnóstico + Wrapper** (seção 6).
5. **Uma página precisa receber blocos independentes?** → **Slots** (seção 8).

Se nenhuma das perguntas 2 a 5 teve "sim", você está na pergunta 1: use props simples.

## 3. Props simples (padrão)

É o ponto de partida para tudo. Um componente com props bem nomeadas é mais fácil de ler, testar e refatorar do que qualquer estrutura composta.

```tsx
<Alert tone="warning" title="Atenção" description="Prazo termina amanhã" />
```

Virar Compound só faz sentido quando a lista de props começa a espelhar a estrutura interna (`headerTitle`, `headerIcon`, `footerActions`, `renderFooter`...). Antes disso, não.

## 4. Compound Component

### Quando usar

Use **somente** se pelo menos um destes for verdade:

- O consumidor precisa **reordenar** as partes.
- O consumidor precisa **omitir** partes de forma frequente e variada.
- O consumidor precisa **intercalar** elementos próprios entre as partes.
- O componente tem partes que se coordenam por estado compartilhado (ex.: Tabs, Accordion, Dropdown).

### Quando NÃO usar

- A estrutura é fixa (sempre header + body + footer, nessa ordem).
- Há apenas dois ou três filhos e ninguém vai mexer na ordem.
- Só existe um consumidor. Espere o segundo.
- O objetivo é "ficar mais flexível" sem um caso concreto pedindo isso.

Um teste rápido: se ao escrever a documentação você não consegue dar um exemplo real de uso em que a ordem ou composição muda, não precisa de compound.

### Convenções

- Subcomponentes ficam na pasta do pai, um arquivo cada: `<pai>-<parte>.tsx`.
- Subcomponentes **não são exportados soltos**; o namespace é a API única.
- `index.tsx` só monta o namespace com `Object.assign(Root, {...})` e reexporta os tipos de props.
- Estado compartilhado entre partes usa Context (seção 5).

```tsx
export const Profile = Object.assign(ProfileRoot, {
  Header: ProfileHeader,
  Tabs: ProfileTabs,
  Tab: ProfileTab,
  TabPanel: ProfileTabPanel,
})
```

### Limite de tamanho

Se o compound passa de **cerca de 5 subcomponentes**, revise. Normalmente há dois componentes distintos escondidos dentro de um.

### Atenção: Server Components (Next.js / RSC)

Se o projeto usa React Server Components, a notação com ponto (`Profile.Header`) pode não funcionar a partir de um Server Component quando o root está em um arquivo `"use client"`, porque a referência ao componente cliente não carrega as propriedades do namespace. Regra: **valide esse caso no projeto antes de adotar o padrão em larga escala**. Se falhar, use exports nomeados para esse componente específico e registre a exceção aqui.

### Atenção: tree-shaking

O namespace via `Object.assign` impede o bundler de descartar subcomponentes não usados. Para a maioria dos componentes isso é irrelevante. Só vale tratar se o componente for pesado (editores, gráficos, bibliotecas grandes dentro dos subcomponentes).

## 5. Context e variantes

### Regra

Context só entra quando **partes distantes do componente precisam ler ou alterar o mesmo estado** (aba ativa, item expandido, seleção).

| Situação | Solução |
| --- | --- |
| Estado compartilhado entre partes (aba ativa, aberto/fechado) | React Context do compound |
| Só variação visual propagada (variante, tema, tom) | Scoped-Variable (CSS variable ou atributo `data-*` no root), **sem Context** |
| Dado que só um filho direto usa | Prop normal |

### Boas práticas de Context

- Um Context por componente composto, interno à pasta dele.
- Hook de acesso (`useProfileContext`) que **lança erro claro** se usado fora do Root.
- Não exponha o Context para fora do componente.
- Não coloque valores que mudam com frequência e não são necessários às partes: isso causa re-render à toa.

## 6. Agnóstico + Wrappers

### Quando usar

Só depois que **dois ou mais domínios reais** precisam do mesmo componente visual (ex.: `Cursos` e `Ies` usam o mesmo painel de filtros). Com um único domínio, escreva o componente direto, com o conhecimento de domínio dentro dele. Quando o segundo domínio chegar, você sabe exatamente o que é comum e o que é diferente, e extrair fica fácil e correto.

### Definições

- **Componente agnóstico:** cuida de apresentação, layout e estado de UI. Nome neutro (`Profile`, `SearchHeader`, `FiltersPanel`). Nunca importa hook ou serviço de domínio.
- **Wrapper de domínio:** conhece hooks, mapeamentos e textos do domínio e consome o agnóstico (`ProfileCursos`, `SearchHeaderIes`).

### Regras

- O agnóstico **nunca** importa hook/serviço de domínio.
- O wrapper deve ser **fino**: configuração + composição. Se o wrapper tem muita lógica própria, a lógica provavelmente pertence a um hook do domínio, não ao wrapper.
- **Convenção de API do wrapper:** por padrão, o wrapper **fecha a composição e expõe apenas props de domínio** (`<ProfileCursos cursoId={id} />`). Só repasse o compound inteiro ao consumidor quando o caso de uso exigir (e documente o motivo no componente).
- Se os wrappers de dois domínios divergem só em configuração, centralize a configuração em um objeto, não em condicionais dentro do agnóstico.

### Quando subir lógica para o agnóstico

A lógica só sobe quando **pelo menos dois wrappers já a usam de forma idêntica**. Não suba por antecipação ("vai ser útil").

Sinais de que subiu cedo demais:

- O agnóstico ganhou props como `isCursos`, `mode="ies"` ou flags por domínio.
- Há `if`/`switch` por tipo de domínio dentro do agnóstico.
- Uma mudança para o domínio A quebra o domínio B.

Se qualquer um destes aparecer, a lógica deve descer de volta para os wrappers, ou virar uma configuração injetada por props.

## 7. Generics e render props

Use generics em componentes de lista quando **mais de um tipo de item** realmente passa por eles (`SearchResults<TItem>`). O domínio entra por props: `renderItem` e `getItemKey`.

- Com um único tipo de item, use o tipo concreto. Generic desnecessário só adiciona ruído.
- `renderItem` inline recria a função a cada render. Em listas pequenas é irrelevante; em listas grandes ou com itens caros, use `useCallback` ou extraia o item para um componente memoizado.
- Prefira `children`/composição a uma prop `render*` quando for só uma parte da estrutura.

## 8. Slots em páginas

Páginas de busca recebem blocos independentes por props nomeadas (`LayoutSearchPage`: `searchHeader`, `filtersPanel`, `results`...). Use slots quando a página define o esqueleto e cada bloco é independente. Mantenha poucos slots (idealmente até 5) e não passe estado entre eles pela página; se blocos precisam conversar, o problema é de estado, não de layout.

## 9. Terminologia

Para evitar ambiguidade, use sempre:

- **Root:** o componente raiz de um compound (`ProfileRoot`).
- **Compound Component:** componente cujas partes são subcomponentes expostos por namespace (`Profile.Header`), montado com `Object.assign(Root, {...})`.
- **Agnóstico:** o componente neutro de domínio.
- **Wrapper:** o componente que aplica o domínio sobre o agnóstico (`<Agnóstico><Domínio>`, em `<agnóstico>/wrappers/`).
- **Scoped-Variable:** o root emite um atributo (`data-module`, `data-variant`) e o CSS reatribui variáveis para toda a subárvore; os filhos só consomem a variável, sem React Context.
- **Slot:** bloco independente recebido por prop nomeada (`searchHeader`, `results`).

Não use "raiz" para falar do componente agnóstico.

## 10. Sinais de over-engineering

Revise a estrutura se algum destes aparecer:

- Um componente com dois filhos fixos virou compound.
- Existe um wrapper para um único domínio.
- O agnóstico tem flags ou condicionais por domínio.
- Há Context usado só para passar uma variante visual.
- Há generics com um único tipo concreto de uso.
- Para alterar um texto você abre mais de três arquivos.
- Um novo desenvolvedor não consegue dizer em quais arquivos mexer sem perguntar.
- Os arquivos de "estrutura" (index, tipos, contextos) são maiores que os de comportamento real.

## 11. Checklist de code review

Antes de aprovar uma PR que adiciona ou muda estrutura de componentes:

1. Existe um caso de uso **atual** (não hipotético) que justifica o padrão?
2. A versão com props simples foi considerada e descartada por um motivo concreto?
3. Compound: o consumidor realmente reordena, omite ou intercala partes?
4. Context: há estado compartilhado de fato, e não só variante visual?
5. Wrapper: existem pelo menos dois domínios usando o agnóstico?
6. Lógica subiu para o agnóstico: dois wrappers já usam de forma idêntica?
7. O agnóstico continua livre de importações de domínio e de flags por domínio?
8. Dá para remover uma camada sem perder funcionalidade? Se sim, remova.

## 12. Exemplo: simplificando

**Antes (over-engineered):** `Card` com `Card.Header`, `Card.Title`, `Card.Body`, `Card.Footer`, Context para o tom, usado sempre na mesma ordem em 12 lugares.

```tsx
<Card tone="info">
  <Card.Header><Card.Title>Resumo</Card.Title></Card.Header>
  <Card.Body>{text}</Card.Body>
</Card>
```

**Depois:** props simples, e a variante resolvida por prop.

```tsx
<Card tone="info" title="Resumo">{text}</Card>
```

Se um dia um consumidor precisar de um segundo bloco entre o título e o corpo, **aí** o Card vira compound, com um caso real em mãos.

## 13. Política de exceções

Qualquer desvio destas diretrizes é aceitável quando justificado. Registre o motivo em um comentário curto no `index.tsx` do componente (uma ou duas linhas). Isso mantém o guia como ponto de partida e evita que ele se transforme em burocracia.
